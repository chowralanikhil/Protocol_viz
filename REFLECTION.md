# Reflection: Application & Transport Layer Lab

I used OpenAI Codex desktop with the GPT-5.6 Codex agent. I chose it because it could turn both assignment briefs into a working browser project, assist with protocol checks, and retain a clear record of AI-assisted work. The agent was used for interpreting requirements, planning the dual-view architecture, building the interface, generating protocol examples, reviewing TCP numbering, and preparing the supporting evidence.

The Assignment 2 extension preserves the original two main panels. The left panel continues to run Browsing, Mail, and Streaming. When the user starts an activity, JavaScript creates both an Application-layer timeline and a Transport-layer TCP timeline for that same action. A shared playback index controls the two timelines. The Application Layer and Transport Layer tabs therefore show different abstractions of the same action, while previous, next, pause/resume, and replay retain one synchronized position. This makes it possible to switch views during a demonstration without losing the selected activity or its current stage.

The most important AI output requiring review was the TCP sequence logic. A TCP handshake is not only three labels: the client SYN consumes one sequence number, the server's SYN-ACK acknowledges that value plus one, and the final ACK acknowledges the server's initial sequence number plus one. During data transfer, the next sequence value must advance by the exact data length; an ACK reports the next byte the receiver expects, rather than the last byte received. The final version also shows advertised receive-window fields, `PSH, ACK` data segments, and orderly connection close: FIN consumes one additional sequence number and is acknowledged before the peer sends its own FIN. I corrected the model around those rules instead of presenting generic arrows without numeric meaning.

The three activities illustrate different TCP usage. Browsing usually has a short request-response exchange after DNS and a TCP handshake. Mail uses a longer, conversational SMTP dialogue, but TCP still carries it as one ordered byte stream; the application commands are not separate transport connections. Streaming makes several HTTP requests for a manifest, quality playlist, and media segments, so its TCP view has repeated data transfers and window acknowledgements. The project presents TCP as the primary transport for those HTTP examples. QUIC and UDP are noted in the assignment as optional extensions and are not claimed by this simulation.

The dashboard remains intentionally simulated: it does not create a live socket, measure real RTT, or implement a full congestion-control algorithm. That choice keeps the behavior deterministic and makes the protocol fields easy to inspect, while retaining the ordering and state transitions expected from real TCP.
